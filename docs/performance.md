# 文件处理性能测试

该工具针对 Windows 后端及其推理子进程。输入任意 CBZ/ZIP，每轮产生独立输出和完整测量证据。它使用新增的 `-perf-json` 埋点，不依赖旧 `bench-json` 或旧性能结论。

## 运行

安装 Python 依赖，并重新构建引擎（已有旧版 exe 不支持新埋点）：

```powershell
python -m pip install -r .\scripts\requirements-bench.txt
$env:CGO_ENABLED='1'
$env:CC="$PWD\runtime\toolchain\mingw64\mingw64\bin\gcc.exe"
$env:PATH=(Split-Path $env:CC)+';'+$env:PATH
go build -o .\bin\mangatrans.exe .\cmd\mangatrans

python .\scripts\bench.py "D:\漫画\输入.cbz"
```

默认正式测量 5 轮，100 ms 采样进程资源，1 s 查询 GPU，单轮超时 3600 s。每轮启动新进程，首轮也保留在汇总中。模型、运行库等设置沿用应用代码中的参数和环境变量。

```powershell
# 显式预热一轮，再测五轮；只处理前十页
python .\scripts\bench.py "D:\漫画\输入.cbz" --warmup 1 --runs 5 --limit 10

# 调整采样，指定一个尚不存在的结果目录
python .\scripts\bench.py "D:\漫画\输入.zip" --interval 0.05 --gpu-interval 0.5 --output-dir .\results\trial-01

# 传入引擎选项，每个 token 使用一个 --engine-arg
python .\scripts\bench.py "D:\漫画\输入.cbz" --engine-arg=-conf --engine-arg=0.4
```

默认结果目录为 `.cache/bench/<时间>/`。已有目录会被拒绝，避免覆盖或误用上一次的输出。输入文件不会被修改。

## 比较两个引擎版本

`compare_bench.py` 按配对运行 before 和 after。每对交替顺序，奇数对先跑 A（before），偶数对先跑 B（after），以减少运行顺序和系统状态变化的影响。默认比较整本输入；用 `--limit` 固定选择页数。脚本会逐页比较输入页名、尺寸、检测数、OCR 接受/失败/拒绝数、翻译数、绘制数和结果状态。工作量不匹配的配对不会进入性能统计。

```powershell
python .\scripts\compare_bench.py "D:\漫画\输入.cbz" --pairs 5 --limit 20 --before .cache/perf-opt/before.exe --after .cache/perf-opt/after.exe --output-dir .cache/perf-opt/compare-20
```

`--output-dir` 必须指向新目录。比较会逐对保存原始测量和清单；若进程中断，可用相同输入、exe、参数和输出目录加 `--resume` 继续。恢复时，输入和 exe 的散列及设置都必须与清单一致。已完成的单轮测量会恢复使用，缺少或不完整的 checkpoint 会停止并要求检查，不能用变更后的文件接续。

少于 5 个有效配对时，报告结论为 `inconclusive`。达到 5 对后也只给描述性比较，不据此证明优化的因果收益。运行期间不要改动输入或 exe。比较记录整卡 GPU 观测值，不是本应用独占的 GPU 用量；相同的 GPU 还必须保持其他负载条件可比。输出校验不验证译文语义，因此应确认两版结果语义和输出质量相当，再解释速度差异。

本次调优记录使用同一文件、同一选择页数（20 页）做 5 轮配对比较。此前单独调高 OCR 并发的试跑从 OCR workers 2 调至 4，OCR 页阶段累计墙钟时间从 20.2 秒降到 18.5 秒，但有效 OCR 块从 153 条变为 152 条。这组结果工作量不匹配，不能作为同工作量提速证据，也不是整个应用的总耗时。

按最终选择，正式对比两版均使用串行 OCR（一个请求），不再进行 OCR 并发调优；并发试跑不计入本次优化收益。

`ocr-workers` 允许 1 到 4，默认 1。它控制 OCR 请求并发，ONNX 检测会话仍串行。`mt-batch-pages` 允许 1 到 4，默认 2；它控制最多多少个连续页面共享一个最多包含 12 个文本块的翻译批次。调整这些参数可能改变输出工作量，比较时应核对实际参数和逐页结果。

## 结果文件

| 文件 | 内容 |
| --- | --- |
| `report.md` | 可读报告：轮次、阶段分布、错误、资源及测量边界 |
| `report.json` | 环境、输入与 exe SHA-256、参数、逐轮结果、成功轮次汇总 |
| `run-NNN/trace.json` | Go 单调时钟原始纳秒事件；页号/框号从 0 开始，-1 为全局 |
| `run-NNN/samples.jsonl` | 各采样时刻的每进程 RSS、CPU、I/O，进程树合计和 Job 累计计数 |
| `run-NNN/gpu.json` | GPU 基线、逐卡采样、查询起止时刻和错误原因 |
| `run-NNN/engine.log` | 引擎原始 stdout/stderr，计时分析不从日志猜阶段 |
| `run-NNN/command.json` | 实际命令参数数组 |
| `run-NNN/result.json` | 本轮状态、耗时、资源、逐页输出校验 |
| `run-NNN/output.cbz` | 本轮实际处理的产物 |

报告在每轮完成后更新。退出码 0 表示正式轮次全部完整成功；1 表示处理失败、降级或输入/exe 发生变化；2 表示测量设施错误；Ctrl+C 返回 130。预热失败仍记录，但不进入正式轮次汇总。

`trace.json` 同时记录实际选择的模型、字体、推理程序和 ORT 库的路径、大小及修改时间，以及 Go 版本；模型元数据不是内容散列。报告只保存 `MANGATRANS_` 前缀的环境配置，不导出整个环境。

## 时间的含义

- 外部墙钟从创建挂起引擎之前开始，到观察到引擎退出为止，包含挂起绑定 Job、启动、处理、清理及写遥测。默认轮询退出，实际观察误差上界估计记录在 `wall_observation_uncertainty_s`，不要把几毫秒差异当成优化收益。
- Windows 内部计时直接读取 QPC 高精度单调计数器，保留纳秒换算原值和硬件计数频率，不在每个框上截断到毫秒。阶段包括输入读取、运行库初始化、模型加载/卸载、解码、裁剪、检测、OCR、翻译批次/补译、气泡布局、擦字、排版、编码、写包/校验及清理。
- `operation` 为顶层操作，覆盖时间用区间并集求和；`nested` 校验及 `request` HTTP 调用位于操作内部，不能重复加总。`uninstrumented_ms` 保留未埋点时间，包括部分控制逻辑、日志、术语表处理和临时目录清理等。
- OCR 页操作的墙钟时间覆盖该页所有 OCR 请求。并发请求的各自耗时可能重叠，不能把嵌套请求时间相加后当作额外页耗时。翻译批次可以跨连续页面，不能随意把一次请求时间按页数分摊。
- `counter` 事件记录擦字阶段的 `inpaint_components`、`windows`、`fills`、`local_fills` 和 `model_calls` 计数。逐页检测框、有效 OCR 块、翻译块和绘制块来自 `pages` 字段，不是 `counter` 事件；这些字段都描述工作量，不是持续时间。
- HTTP 事件覆盖请求序列化至响应读取、解析完成；记录内部重试和 JSON schema 兼容重发，包括失败请求。翻译阶段总时间已包含这些请求，不能再加一次。
- 这是调用者观察到的延迟，包含图像预处理、传输、等待 GPU、后处理等，不是独立的 CUDA kernel profiler。
- 输入/exe 散列、预检和外部输出校验位于计时区域之外。输入散列会预热 OS 文件缓存，因此首轮不能称为严格冷缓存。没有清理操作系统缓存。
- 事件先积累在引擎内存中，结束时写盘，其内存和记录开销也计入被测进程。报告序列化和写盘在内部总计时之外，但包含在外部总耗时中。

## 资源的含义

引擎以挂起状态创建，在执行任何应用代码前绑定 Windows Job Object，再恢复运行。其子进程自动继承 Job。操作系统累计 CPU 用户态/内核态时间、I/O、缺页数及提交内存峰值，因此已经退出的 OCR 服务器也会被计入。绑定失败直接报测量设施错误，不退回不完整的资源统计。

CPU 秒除以墙钟秒为平均使用的核数；再除以逻辑核数才是整机百分比。CPU 时间不是耗时，多个核并行时可超过墙钟。Job 的 I/O 是操作系统向进程归属的操作/字节计数，可能含缓存、文件映射以外的其他设备操作，不能声称是物理磁盘读写量。

RSS 是同轮依次观测的进程工作集之和，并非原子快照；共享页可能重复计数，短命进程和短暂峰值可能漏采。`peak_job_commit_bytes` 是系统记账的 Job 提交内存峰值，与 RSS 含义不同。进程采样发现采用进程树遍历，不能保证枚举出采样间隔内诞生又退出的进程；Job 的累计值覆盖它们。每轮保留实际采样间隔和采样开销，不能用理想间隔冒充实际精度。

Go 事件与 Python 的 `perf_counter_ns` 使用同一 Windows QPC 时钟，原点在报告中保留。频率倒数决定计数粒度，函数调用和采样仍有开销。阶段 RSS/GPU 仅使用采集窗口完全位于阶段内的样本；阶段 CPU 仅累计这类相邻采样窗口的 Job CPU 增量，并列出覆盖的窗口时长，不能当成阶段完整 CPU 时间。操作系统 CPU 计数的更新粒度仍会影响归属。跨边界窗口舍弃，短阶段没有样本时留空，不插值制造数据。GPU 利用率还带有驱动自己的历史采样窗口，因此阶段查询也不等于该阶段独立的 GPU 使用率。

GPU 单独线程查询 `nvidia-smi`，不会让慢查询阻塞进程采样。记录每张卡的显存、GPU/内存利用率、功耗、温度及驱动版本；缺项为 null，并保留错误。所有数值是整张卡的观测值，包含其他应用；WDDM 下不能据此可靠地推算本应用独占显存。分布按有效样本统计，非连续积分或时间加权平均。基线单独保留，不能直接相减后称为精确应用用量。

测量本身有开销。默认频率适用于数十秒以上的处理任务；很短的调用应看内部事件。若关心采样扰动，应以相同输入和参数、交错运行不同采样频率，再比较完整耗时的分布，不能预设零开销。

## 成功、失败与重复性

逐页统计检测框、无效裁剪、OCR 失败、空白/噪声 OCR、有效 OCR、接受译文、真正绘制的文本数量，以及解码/检测/擦字/排版/编码失败和无译文页。OCR 失败、有效 OCR 未被翻译、页回退、零文本绘制都会被标记为失败或降级。请求出错后恢复完整结果的轮次标为 `ok_with_recovered_errors`，其错误和重试耗时均保留，并进入成功汇总，避免排除较慢的成功样本。没有文字的合法漫画也可以生成产物，但不能伪装成完整翻译工作量来汇总。

脚本重新读取输出 ZIP，核对页名、自然排序、数量和 CRC，并完整解码所有图像，检查尺寸、应保留页面的字节一致性、应绘制页面的字节变化。它不能证明翻译语义正确或文字视觉效果正确。

仅完整成功轮次进入汇总，报告同时给出失败数量和每个失败轮次的实际耗时。每个阶段给出累计时间、调用数、错误数、最小/中位/p95/最大值；重复轮次给出中位数、范围和标准差。p95 用 nearest-rank 算法，5 轮的 p95 就是最大值，不应解释成稳定尾延迟。

相同配置至少跑 5 轮后再判断重复性。阶段时间和 CPU/GPU 占用用于定位进一步剖析方向，不能单独证明瓶颈的因果关系。

## 验证脚本

```powershell
python -m unittest discover -s scripts -p test_bench.py -v
```

包括真实 Windows 子进程的 CPU/I/O 累计、已退出子进程计数、进程树超时清理、异常退出，以及嵌套区间去重、失败轮次排除和损坏图像拒绝。

运行测试时可用 `--limit` 验证少量页面；正式比较应使用相同文件和相同选择页数。`--limit` 在应用读完整个压缩包后才截取页面，因此限制页数不会将输入读取变成仅读取这几页。
